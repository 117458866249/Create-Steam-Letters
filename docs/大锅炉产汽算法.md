# 大锅炉产汽算法

本文描述 Create 大锅炉 (FluidTank 多方块 + BoilerData)在本模组下的产汽机制: 水与热源进入, 蒸汽进入锅炉缓冲,
供蒸汽引擎直抽与青铜蒸汽泵抽出.

## 0. 术语与量纲

| 记号 | 含义                                   | 单位          |
|------|----------------------------------------|---------------|
| H    | 底部热源热量之和(activeHeat)           | 级            |
| V    | 锅炉体积给的等级上限(boilerSize / 4)   | 级            |
| Lf   | 连续锅炉等级                           | 级            |
| C    | 单台满额引擎的耗汽基准                 | mB/t          |
| R    | 水汽比(每 mB 水产生的蒸汽量)           | mB 汽 / mB 水 |
| P    | 每 tick 产汽量                         | mB/t          |
| B    | 蒸汽缓冲存量 / 容量                    | mB            |
| Wt   | 水罐存量 / 容量                        | mB            |

基准常数取自本模组引擎默认参数: 满额应力 16384 SU, 满额耗汽 12 mB/t, 因此 1 mB/t 蒸汽对应约 1365.333 SU 产能力.

## 1. 连续锅炉等级

Create 原版取整数等级:

```
L = min(activeHeat, floor(boilerSize / 4), floor(waterSupply / 10), 18)
```

本模组改为连续值, 不取整, 并把供水项换成水罐判定:

```
Lf = min(H, V, 18)   水罐里有水时
Lf = 0               水罐见底时
V  = boilerSize / 4.0
```

Lf 的物理含义是「这台锅炉能同时喂饱的满额引擎台数」, 也就是名额数. 它被热与体积两者夹住, 再被水罐存量整体否决.

供水项之所以从连续的 `waterSupply / 10` 换成对水罐的二值判定, 是因为 Create 的供水计量只认流经量: 一旦为了省水停止注水,
`waterSupply` 会在约 50 tick 内衰减到 0, 等级随之中断, 接入的设备连缓冲里的存量蒸汽都用不上, 形成死锁. 水罐把「供得动」
与「流进来多少」解耦: 只要罐里还有水就按满额供水处理, 水被抽干才归零, 衰减过程由存量本身表达.

配置 `WATER_PER_BLOCK` 置 0 时没有水罐, 退回 Create 的采样口径, 即 `Lf = min(H, V, waterSupply / 10.0, 18)`.

## 2. 产汽

```
P_nom   = Lf * C                      名义产汽, 等于「喂饱 Lf 台引擎所需」
P_water = Wt / (waterMultiplier / R)  水罐存量能支撑的产汽量
P_space = B_capacity - B_amount       缓冲剩余空间
P       = min(P_nom, P_water, P_space)
```

每 tick 执行 (完整顺序见第 7 节):

```
B_amount += floor(P)                  过热时 P_nom 先除以 SUPERHEATED_WATER_MULTIPLIER
Wt       -= ceil(P / R * waterMultiplier)
```

水汽比默认 `R = 1.2`(等价于每 mB 蒸汽耗水 10/12 = 0.8333 mB). 取这个值的理由: Create 的供水门槛是每级 10 mB/t, 而每级产汽是
12 mB/t, 只有 1.2 才能让「烧掉的水」与「等级门槛要求的水」完全对齐, 水罐的收支才自洽.

`P_water` 项使存量不足表现为连续减产: 罐里的水撑不起满产时按比例缩小产量, 不会出现产出的蒸汽多于烧掉的水. 水被抽干时 P 归零.

### 水罐

水罐是 BoilerData 上的 `@Unique` 字段, 不是 `tankInventory`:

```
Wt_capacity = boilerSize * WATER_PER_BLOCK   默认每方块 1000 mB
Wt          <= Wt_capacity
```

注水走 `SteamBoilerFluidHandler.fill`: 水存进水罐, 罐满则返回 0 让管网自己憋住. 罐满拒收之所以安全, 正是因为等级由存量支撑,
不再依赖 Create 的流入量采样. 水罐不存在 (`WATER_PER_BLOCK = 0`) 时退回原版做法, 即水一进来就被采样并消耗掉.

产汽时水从水罐里扣, 因此锅炉不再「流进多少就烧掉多少」: 管网可以按需间歇供水, 水罐负责把供水与耗汽削峰填谷.

### 蒸汽类型

产出普通蒸汽还是过热蒸汽, 按等级判定:

```
若 Lf >= SUPERHEATED_AT_LEVEL (默认 18)  -> 过热蒸汽
否则                                     -> 普通蒸汽
```

满级需要同时满足热源 18, 体积 >= 72 方块, 水罐不被抽干, 代价很高, 因此把过热产出绑在满级上是唯一不会随手白拿的门槛.

过热蒸汽的水汽比放大到 `R / SUPERHEATED_WATER_MULTIPLIER`(默认 1.5, 与引擎的过热输出倍率一致), 即同样的 P 需要 1.5
倍的水:

```
waterUsed = P / R * (过热 ? SUPERHEATED_WATER_MULTIPLIER : 1.0)
```

不这么做的后果很直接: 过热蒸汽让引擎耗汽减半, 输出 1.5 倍, 若产汽成本不变, 满级锅炉等于凭空多出 3 倍产能.

## 3. 蒸汽缓冲与出口

蒸汽不落进 `tankInventory`(那里存水), 而是在 BoilerData 上用 `@Unique` 字段维护虚拟缓冲:

```
B_capacity = boilerSize * 1000 * BUFFER_MULTIPLIER   默认倍率 1.0
B_fluid    = NONE | NORMAL | SUPERHEATED             当前缓冲中的蒸汽类型
```

缓冲同一时刻只容纳一种蒸汽. 若目标类型与 `B_fluid` 不同且缓冲非空, 则本 tick 不产汽, 等管网把旧蒸汽抽空后再切换类型,
避免凭空把普通蒸汽转成过热蒸汽.

出口只有一个: `SteamBoilerFluidHandler.drain` 从 B_amount 抽, `getFluidInTank` 报告缓冲内容. 于是所有通过 capability
取汽的路径共享同一个蒸汽池:

- 蒸汽引擎贴锅炉直抽 (`SteamEngineBlockEntity.drawFromBoiler` 走背后方块的 FLUID_HANDLER)
- 青铜蒸汽泵贴锅炉抽汽进管网
- 管道与其他容器

缓冲满时 `P_space = 0`, 只停止产汽, 水继续存进水罐直到罐满, 罐满后管网自然背压. 于是「蒸汽没人要」不再等于「水被白烧」,
这是水罐存在的主要目的: 玩家可以把产出的蒸汽攒着, 也可以在无人抽汽时让锅炉与水网一起停住.

### 护目镜

护目镜显示额定产汽 `Lf * C`, 与 Create 显示应力产能的口径一致: 它由热源与体积夹出的等级决定, 水罐见底时读数立即下降,
不会出现满读数配空缓冲的假象. 实际写进缓冲的量还额外受缓冲剩余空间与水罐存量限制, 因此可能低于这个读数.

水罐存在时, 护目镜还会多一行储水 `Wt / Wt_capacity`.

数值在客户端由同步过来的字段直接算出, 不需要额外的网络包: 这些字段写在 `BoilerData.write` 里, 而 `write` 会被
`FluidTankBlockEntity` 的 `saveAdditional` 与 update tag 一起带上.

## 4. 名额摊薄

名额不在注册阶段硬性拒绝. 默认 (`STRICT_QUOTA = true`) 由显式份额实现:

```
N     = 接入的引擎数 + 泵数
share = min(1, Lf / N)
```

引擎与泵共享同一份名额. 名额满 (N > Lf) 之后再加装一台设备, 每台设备的份额都按 N 摊薄, 于是加装蒸汽泵会压低每一台引擎的应力输出.

份额落在 `BoilerData.getEngineEfficiency`, 对 Create 原版蒸汽引擎与名额池合流:

- Create 的蒸汽引擎不消耗流体, 应力上限完全由该效率决定, 因此只有覆写效率才能让泵占名额这件事对它们成立
- 被动热源(营火一类)的效率上限远低于 1, 名额摊薄只按设备数分摊这块, 不能把它补回去
- 本模组自己的蒸汽引擎不额外乘份额: 它真抽汽, 泵抽走蒸汽时它自然掉档, 再乘一次等于双重惩罚

关闭 `STRICT_QUOTA` 时退回纯流量摊薄:

```
锅炉每 tick 只产出 Lf * C 的蒸汽
每台满额引擎每 tick 想要 C
```

接入设备的总需求超过 P 时, 谁抽到多少就决定谁的档位, 引擎自身已有的 `档位 = 到手蒸汽 / 满额需求` 机制会自动压低 SU.
该模式下泵抽走的蒸汽同样会减少引擎可得的蒸汽, 但份额不会显式钉死, 因此引擎自带的内部储罐 (不经过锅炉) 不参与摊薄.

## 5. 设备侧

### 蒸汽引擎

无需改动即可消费缓冲蒸汽: 现有 `drawFromBoiler` 已从背后方块的 `FLUID_HANDLER` drain, 每 tick 上限为
`ceil(getTargetConsumption())`, 到手比例决定 4 档应力.

Create 引擎的效率被覆写成 `share = min(1, Lf / 设备数)`, 也就是它的 SU 上限按名额钉死. 本模组自身的蒸汽引擎只走流量摊薄,
它从锅炉直抽的上限仍是 `ceil(getTargetConsumption())`.

引擎护目镜里的应力百分比按 `实际应力 / 目标应力` 计算, 因此加了份额之后读到的数字与实际 SU 一致.

### 青铜蒸汽泵

抽汽速率不由本模组指定, 交给 Create 的管网流动机制:

```
泵作为压力源工作, 压力 = 转速
青铜泵不受应力限制, 转速恒为 AllConfigs.server().kinetics.maxRotationSpeed
锅炉侧只需要 handler.drain 能返回缓冲蒸汽
实际抽汽量 = 管网在当前压力下的搬运量, 随转速线性上升, 随泵数量线性叠加
```

因此不存在"单泵抽汽上限"这项配置. 泵越多, 压力路径越短, 抽走锅炉蒸汽就越快; 反过来, 泵抽得快会更快掏空缓冲, 也更快占满名额.

识别条件与引擎一致: 从锅炉方块沿某个方向看过去是泵, 且泵的 `state.getValue(FACING)` 等于该方向 (与 Create 判断蒸汽引擎的
`SteamEngineBlock.getFacing(attachedState) == d` 同一口径). 泵的抽汽侧是 FACING 的背面, 因此这样贴上去的泵正好从锅炉抽汽.

统计时机不能只挂在 `BoilerData.evaluate` 上: Create 只在锅炉自身的方块变化与蒸汽引擎的放置 / 破坏时调用
`FluidTankBlock.updateBoilerState`, 往锅炉旁边放一台泵不会走到那里, 泵数会一直停在 0, 名额也就摊不开. 因此泵数由
`FluidTankBlockEntity.tick` 每 5 tick 补扫一次写回 (与供水采样同一节拍), `evaluate` 那条路径保留用于结构变动时立刻刷新.

只挂泵不挂引擎时锅炉也必须是活的, 否则不会扫描热量与采样供水, 产汽无从谈起, 所以 `isActive` 把泵计入.

需要注意青铜泵现有的安全门逻辑: 只要抽取侧管网中存在非蒸汽流体就整体停泵. 锅炉 handler
只会给出蒸汽, 与这条判定不冲突, 但若玩家把水与蒸汽混接在同一张管网, 泵会整体挂起.

## 6. 模式互斥: 蒸汽输入

现有实现允许把蒸汽灌进锅炉当供水与热源 (`steamHeatLevel` 为 9 或 18). 该模式与自产汽互斥:

```
若 steamHeatLevel > 0   -> 处于蒸汽输入模式
    不产汽, 不扣水, 缓冲与水罐都保持原值
    等级仍由蒸汽输入决定(activeHeat 被顶到 9 或 18)
否则                    -> 自产汽模式, 按第 2 节执行
```

退出条件沿用现有采样: 一个完整采样窗口内没有蒸汽输入后 `steamHeatLevel` 归 0, 自动切回自产汽.

## 7. 每 tick 执行顺序

```
1. 若结构变动: 重算 B_capacity 与 Wt_capacity, 夹住 B_amount 与 Wt
2. 采样时刻(每 5 tick): 更新 waterSupply, 更新 steamHeatLevel 状态机
3. 若 steamHeatLevel > 0: 跳过产汽, 结束
4. Wt <= 0 或 B_amount >= B_capacity: 结束
5. Lf = min(activeHeat, boilerSize / 4.0, 18)
6. 目标类型 = Lf >= SUPERHEATED_AT_LEVEL ? 过热 : 普通
7. 若 B_amount > 0 且 B_fluid != 目标类型: 结束(等抽空)
8. P = min(Lf * C / waterMultiplier, Wt / (waterMultiplier / R), B_capacity - B_amount)
9. 加缓冲 floor(P), 扣水 ceil(P / R * waterMultiplier), B_fluid = 目标类型
```

产汽逻辑挂在 `BoilerData.tick`, 与 Create 的采样节拍共用同一个 tick 入口, 不引入独立 ticker.

## 8. 边界与不变量

| 情形             | 行为                                                          |
|------------------|---------------------------------------------------------------|
| 无热源           | `activeHeat = 0` -> `Lf = 0` -> 不产汽                        |
| 体积不足         | `boilerSize < 4` -> `V < 1` -> 产汽按 V 缩小                  |
| 水罐见底         | `Wt = 0` -> `Lf = 0` -> 不产汽                                |
| 水罐满           | `fill` 返回 0, 管网背压; 等级由存量支撑, 不受影响             |
| 缓冲满           | `P_space = 0` -> 不产汽, 水继续存罐直到罐满, 不再白烧水       |
| 只挂泵不挂引擎   | `isActive` 必须为真, 否则锅炉不加热, 不采样, 形成死锁         |
| 被动热源(营火)   | `activeHeat <= 1` -> `Lf <= 1` -> 上限 12 mB/t                |
| 蒸汽输入模式     | 完全不产汽, 缓冲与水罐冻结                                    |
| 存档读档         | 缓冲, 水罐, 泵计数与模式状态需持久化, 否则重启后凭空消失       |
| 等级跌破过热门槛 | 目标类型切回普通, 缓冲中剩余过热蒸汽抽空前不产汽              |
| 名额不足         | `N > Lf` -> `share = Lf / N` -> 每台引擎应力按比例下降        |
| 泵转速           | 恒为 maxRotationSpeed, 抽汽速率由泵数量与管网结构决定         |

## 9. 注入点

| 目标                                               | 方式                                                     |
|----------------------------------------------------|----------------------------------------------------------|
| `BoilerData.evaluate`                              | 统计贴锅炉的青铜蒸汽泵数量(新增 `sl$attachedPumps`)      |
| `FluidTankBlockEntity.width` / `.height`           | `IFluidTankBlockEntityAccessor` 读取, 用于按结构表面遍历  |
| `SteamBoilerFluidHandler.fill`                     | 水存入水罐, 罐满拒收; 蒸汽登记给 `sl$notifySteamInput`   |
| `BoilerData.isActive`                              | 泵计入活性判定                                           |
| `BoilerData.tick`                                  | 结算产汽, 扣水, 夹住缓冲与水罐上限                       |
| `BoilerData.getMaxHeatLevelForWaterSupply`         | 水罐有水时把供水等级顶满, 防止等级随采样塌陷             |
| `SteamBoilerFluidHandler.drain` / `getFluidInTank` | 暴露缓冲蒸汽                                             |
| `BoilerData.getEngineEfficiency`                   | 按 `share = min(1, Lf / 设备数)` 覆写                    |
| `BoilerData.addToGoggleTooltip`                    | 追加额定产汽与储水两行                                   |
| `BoilerData.write` / `read`                        | 持久化缓冲, 水罐与泵计数, 并随 update tag 同步给客户端   |

## 10. 配置项

| 配置                         | 默认  | 说明                                          |
|------------------------------|-------|-----------------------------------------------|
| BASE_CONSUMPTION             | 12.0  | 单台满额引擎耗汽基准, 产汽按它折算名额          |
| STEAM_PER_WATER              | 1.2   | 每 mB 水产生的蒸汽量                          |
| WATER_PER_BLOCK              | 1000  | 水罐容量相对锅炉方块数的倍率(每方块 mB, 0 关闭) |
| BUFFER_MULTIPLIER            | 1.0   | 缓冲容量相对锅炉方块数的倍率(每方块 1000 mB)  |
| STRICT_QUOTA                 | true  | 是否改用显式份额而非流量摊薄                  |
| SUPERHEATED_AT_LEVEL         | 18.0  | 产出过热蒸汽所需的连续等级                    |
| SUPERHEATED_WATER_MULTIPLIER | 1.5   | 过热蒸汽的水耗倍率                            |
