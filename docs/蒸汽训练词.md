# 声明与约定

* `(C)` 表示可配置, 所有可配置参数必须提供明确的默认值.
* 蒸汽和水的转换比例为 `1:1`, 即消耗 `1mB` 水产生 `1mB` 蒸汽.
* 时间单位优先使用 Minecraft tick, 默认 `20 tick = 1秒`.
* 流体容量的单位为 `mB`.
* 生产速率和消耗速率的单位为 `mB/tick`.
* 为了整合包的兼容性, 锅炉输出的蒸汽默认为 `steam_letters:steam`, 但允许通过配置文件修改输出蒸汽的流体 ID.
* 修改蒸汽流体配置时, 不得自动转换, 清除或销毁世界内已有的流体. 如果需要清理旧流体, 由整合包开发者自行处理, 以避免不必要的性能开销.
* 所有设备必须正确处理客户端与服务端的逻辑, 实际的燃料消耗, 流体消耗和生产计算必须在服务端执行.
* 所有需要持久化的数据必须正确保存和读取, 避免设备因区块卸载, 重新加载或游戏重启而丢失工作状态.
* 实现前必须先检查项目现有的方块注册, BlockEntity, 配置, 配方, 流体和动力系统, 优先复用现有架构.
* 如果需求存在歧义或缺少必要参数, 应先列出需要确认的问题, 不得擅自决定核心机制.

# 用法与工作机制

## 1. 太阳能锅炉

太阳能锅炉是一种能够利用太阳光或人造光, 消耗内部存储的水并将其转换为蒸汽的设备.

### 1.1 太阳光条件

* 检查设备正上方 1 至 16 格的空间.
* 如果检查范围内不存在符合遮罩判定条件的方块, 则满足无遮挡条件.
* 玻璃, 树叶以及其他非完整方块按照透明方块处理, 不构成太阳光遮罩.
* 太阳光条件下的基础效率为 `100% (C)`.

### 1.2 人造光条件

* 当太阳光条件不满足时, 可以尝试通过人造光满足工作条件.
* 人造光的最低光照等级默认为 `8 (C)`.
* 满足人造光条件时, 基础效率为 `50% (C)`.

### 1.3 天气影响

* 普通雨天的效率系数为 `50% (C)`.
* 雷雨天的效率系数为 `25% (C)`, 包括雷雨期间的降雪天气.
* 天气效率系数乘以当前光照条件的基础效率.
* 天气影响不得与基础光照效率混淆.

例如, 人造光基础效率为 `50%`, 普通雨天效率系数为 `50%`, 则最终效率为 `25%`.

### 1.4 末地规则

* 末地环境下, 如果设备满足无遮挡条件, 则光照效率为 `100%`.
* 如果设备受到遮罩, 则尝试按照人造光规则判断是否能够工作.
* 末地规则覆盖普通光照效率和天气效率规则, 不受天气影响.

### 1.5 蒸汽生产

* 太阳能锅炉的基础产出速率由注册参数 `production(number)` 决定.
* `production` 表示设备在 `100%` 效率下每 tick 的基础蒸汽产出量, 单位为 `mB/tick`.
* 太阳能锅炉的 `capacity` 默认为 `4000`, `production` 默认为 `12.0`.
* 太阳能锅炉满日照 (`100%` 环境效率) 下的最高产汽速率, 与同材料蒸汽引擎的最高蒸汽消耗速率相等.
* 实际生产速率等于基础产出速率乘以当前环境效率.
* 太阳能锅炉的内部水量不足或蒸汽存储空间不足时, 不得消耗超过实际生产需求的水.
* 蒸汽生产必须支持小数累计, 不得因为每次计算取整而丢失流体.
* 设备停止工作时, 保留内部已有的水和蒸汽.

## 2. 燃烧室与锅炉

燃烧室和锅炉是一套设施, 由两个独立方块组成.

* 燃烧室位于下方.
* 锅炉位于燃烧室上方.
* 燃烧室负责消耗燃料并产生热量.
* 锅炉负责消耗水并生产蒸汽.
* 固体燃烧室和流体燃烧室使用相同的热量机制, 但燃料获取方式不同.

### 2.1 基本工作流程

1. 在燃烧室中输入燃料.
2. 燃烧室开始消耗燃料并升温.
3. 锅炉检测正下方是否存在有效的燃烧室.
4. 当燃烧室热量达到规定条件且锅炉内部存在水时, 锅炉开始生产蒸汽.
5. 当燃料耗尽且没有新的燃料输入时, 燃烧室停止升温并开始降温.
6. 当燃烧室热量低于工作要求时, 锅炉停止生产蒸汽.
7. 当前燃烧的是过热燃料且热量达到最高热量后, 锅炉进入过热状态, 改为生产过热蒸汽, 详见 2.5.

### 2.2 热量机制

燃烧室的热量范围为 `0-100`, 初始热量为 `0`.

* 输入有效燃料后, 燃烧室开始工作.
* 燃烧室每 `2 tick` 增加 `1` 点热量, 直到达到 `100`.
* 燃烧室达到 `100` 点热量后, 不再继续升温.
* 燃料的燃烧时间由对应燃料系统决定.
* 固体燃料和流体燃料本身只决定燃烧持续时间, 不直接决定升温速度.
* 燃烧室有燃料燃烧时, 即使热量已达到 `100`, 燃料仍然持续消耗.
* 当当前燃料耗尽且没有新的燃料输入时, 燃烧室停止升温并开始降温.
* 降温速度应当使用统一的配置参数, 具体默认值需要在实现前确认.
* 热量不得超过当前热量上限, 也不得低于 `0`.

配方带有 `superheated` 标记的燃料称为过热燃料. 过热燃料燃烧时:

* 热量上限从最高热量的 `100%` 提升到 `200%`.
* 热量低于 `100%` 时, 升温速度乘以过热升温倍率, 该倍率由配置项 `superheated_heatup_multiplier` 指定.
* 热量达到 `100%` 后, 升温速度回落到正常速度, 并继续升温到 `200%`.
* 热量低于 `100%` 时, 锅炉行为与非过热燃料完全一致, 仍然生产普通蒸汽.
* 热量达到 `100%` 时进入过热状态, 锅炉在此时清空输出 Tank 中的普通蒸汽并改为生产过热蒸汽.
* 过热状态下热量高于 `100%` 的部分以双倍速度回落, 回落到 `100%` 后恢复正常的降温速度, 同时退出过热状态.
* 点燃下一份非过热燃料后, 过热燃料标记立即清除, 热量被钳回最高热量.
* 过热状态由燃烧室根据「当前燃料是否为过热燃料」与「当前热量是否达到最高热量」共同判定, 锅炉只读取该状态, 不自行判断.

燃烧室负责维护自身的热量数据.

锅炉直接读取正下方燃烧室的当前热量, 不需要额外维护一份重复的热量数据.

如果锅炉正下方不存在有效燃烧室, 或燃烧室被移除, 替换, 则锅炉必须停止生产蒸汽.

### 2.3 锅炉运行效率

锅炉的运行效率根据燃烧室当前热量采用阶梯式计算, 而不是线性计算.

| 燃烧室热量 | 锅炉运行效率 |
|------------|--------------|
| `0-24`     | `0%`         |
| `25-49`    | `25%`        |
| `50-74`    | `50%`        |
| `75-99`    | `75%`        |
| `100`      | `100%`       |

具体规则如下:

* 热量低于 `25` 时, 锅炉停止生产蒸汽.
* 热量达到 `25` 时, 锅炉以基础产出速率的 `25%` 运行.
* 热量达到 `50` 时, 锅炉以基础产出速率的 `50%` 运行.
* 热量达到 `75` 时, 锅炉以基础产出速率的 `75%` 运行.
* 热量达到 `100` 时, 锅炉以 `100%` 的基础产出速率运行.
* 燃烧室降温时, 锅炉根据当前热量重新计算运行效率.

### 2.4 锅炉流体存储

锅炉的 BlockEntity 拥有两个 FluidTank, 两个 Tank 的容量相同.

* 输入 Tank 仅接受水流体.
* 输出 Tank 仅接受配置文件指定的普通蒸汽流体与过热蒸汽流体.
* 两个 Tank 均支持正常的流体能力交互.
* 输入和输出 Tank 的容量均由注册参数 `capacity(number)` 决定.
* 输出 Tank 容量不足时, 锅炉不得消耗超过实际可生产容量的水.
* 锅炉停止工作时, 保留两个 Tank 中的现有流体.
* 不得在流体生产过程中无故销毁水或蒸汽.
* 修改蒸汽流体配置后, 不得自动替换现有 Tank 中的流体.
* 蒸汽生产必须支持小数累计, 不得因为每次计算取整而丢失流体.

锅炉的基础产出速率由注册参数 `production(number)` 决定.

`production` 表示锅炉在 `100%` 运行效率下每 tick 的基础蒸汽产出量, 单位为 `mB/tick`.

实际生产速率等于基础产出速率乘以当前锅炉运行效率.

锅炉的 `capacity` 默认为 `10000`, `production` 默认为 `12.0`.

锅炉的最高产汽速率 (`production` × `100%` 运行效率) 与同材料蒸汽引擎的最高蒸汽消耗速率 (`consumption`) 相等,
一台锅炉刚好喂饱一台同材料引擎.

### 2.5 过热状态与过热蒸汽

燃烧室热量达到最高热量并进入过热状态之后, 锅炉才停止生产普通蒸汽, 改为生产过热蒸汽.
热量低于最高热量时, 即使燃烧的是过热燃料, 锅炉仍按 2.3 的阶梯效率生产普通蒸汽.

* 过热蒸汽的流体 ID 由配置项 `output_superheated_steam_fluid` 指定.
* 过热蒸汽的产出速率默认低于普通蒸汽, 倍率随热量在过热区间中的位置分四段递增, 见下表.
* 过热蒸汽的水耗比与普通蒸汽相同, 每消耗 `1mB` 水产出的体积相同.
* 余额累计在进入过热生产时归零, 不跨状态结转.
* 过热状态下, 锅炉只向输出 Tank 写入过热蒸汽, 不再写入普通蒸汽.
* 热量回落到最高热量以下时, 锅炉恢复生产普通蒸汽, 输出 Tank 中已有的过热蒸汽原样保留.

过热蒸汽的实际生产速率等于基础产出速率乘以运行效率, 再乘以过热产率倍率.

过热产率倍率按热量在过热区间 (最高热量到热量上限之间) 中的位置分四段, 每段的上界由配置项给出:

| 热量区间                              | 倍率配置项                 | 默认倍率 |
|---------------------------------------|----------------------------|----------|
| 最高热量 至 `superheated_threshold_1` | `superheated_production_1` | `0.75`   |
| `superheated_threshold_1` 至 `2`      | `superheated_production_2` | `0.85`   |
| `superheated_threshold_2` 至 `3`      | `superheated_production_3` | `0.95`   |
| `superheated_threshold_3` 至 热量上限 | `superheated_production_4` | `1.0`    |

三个阈值的默认值依次为 `125`, `150`, `175`, 单位为热量占最高热量的百分比.

因此热量刚越过最高热量时产率最低, 越接近热量上限产率越高; 达到最高倍率时过热蒸汽的产率与同条件普通蒸汽持平.
倍率允许配置到 `1.0` 以上, 也可以在 `0.0` 处完全停止过热生产.

输出 Tank 是单流体容器, 无法同时容纳普通蒸汽与过热蒸汽. 因此进入过热状态时, 必须先让输出 Tank 中的普通蒸汽消失,
之后才能填入过热蒸汽.

清空只发生在进入过热状态的那一刻, 之后持续生产过热蒸汽期间不再重复清空.

输出 Tank 中已有的普通蒸汽有两种处理方式, 由配置项 `do_overheated_steam_replace` 决定:

| 取值    | 行为                                                            |
|---------|-----------------------------------------------------------------|
| `false` | 一次性销毁输出 Tank 中的全部普通蒸汽, 之后生产过热蒸汽. 默认值. |
| `true`  | 把输出 Tank 中现有的普通蒸汽就地替换为等量的过热蒸汽.           |

两种方式都不额外消耗水, 也不影响已经写在 Tank 中的数量.

普通蒸汽流体与过热蒸汽流体配置为同一个 ID 时, 配置加载失败.

### 2.6 输出 Tank 停摆

过热蒸汽被抽走之前, 如果热量已经回落到最高热量以下, 锅炉会尝试生产普通蒸汽, 但单流体罐装不下,
于是进入停摆状态:

* 水按当前运行效率对应的产率被照常消耗, 但不产出任何流体.
* 输出 Tank 中的过热蒸汽原样保留, 直到被抽走.
* 停摆期间余额归零, 恢复生产后重新从 `0` 开始累计.
* 输出 Tank 被抽空后, 锅炉在下一个 tick 恢复正常生产.

停摆只是为了让玩家取走已经产出的过热蒸汽, 不额外补偿被消耗的水. 保留下来的过热蒸汽本身就是这一段生产的
全部价值, 因此不另设折算或返还机制.

上述停摆只在输出 Tank 中装着「另一种」蒸汽时成立. 罐里正是当前该产的那种蒸汽而仅仅装满时, 仍按 2.4 的规则
处理, 锅炉不会消耗水.

## 3. 固体燃烧室

固体燃烧室用于消耗物品燃料并为锅炉提供热量.

### 3.1 原版燃料支持

* 固体燃烧室默认支持所有被原版熔炉燃料系统识别为可燃燃料的物品.
* 原版燃料的基础燃烧时间使用原版燃料系统提供的燃烧时间.
* 如果物品既匹配自定义燃料配方, 又属于原版燃料, 则优先使用自定义配方的 `time`.
* 如果没有匹配到自定义燃料配方, 则回退到原版熔炉燃料系统.
* 如果两者均不匹配, 则物品不能作为燃料.

固体燃烧室的 `maxHeat` 默认为 `100.0`.

### 3.2 自定义固体燃料配方

固体燃烧室支持通过 RecipeType `steam_letters:solid_fuel` 添加自定义固体燃料.

本配方继承机械动力的处理配方 (`com.simibubi.create.content.processing.recipe.ProcessingRecipe`), 因此使用 Create 处理配方的
JSON 结构.

燃料物品写在 `ingredients` 数组中, 且必须且只能有一项, 形如 `{"item": "..."}` 或 `{"tag": "..."}`.

燃烧时间由 `processingTime` 定义, 单位为 tick, 表示该燃料能够持续燃烧的时间.

`results` 为必需字段, 本配方不产出物品, 固定为空数组.

配方格式如下:

单个物品:

```json
{
	"type": "steam_letters:solid_fuel",
	"ingredients": [
		{
			"item": "minecraft:diamond"
		}
	],
	"results": [],
	"processingTime": 1200
}
```

物品标签:

```json
{
	"type": "steam_letters:solid_fuel",
	"ingredients": [
		{
			"tag": "forge:ingots/iron"
		}
	],
	"results": [],
	"processingTime": 600
}
```

过热燃料:

```json
{
	"type": "steam_letters:solid_fuel",
	"ingredients": [
		{
			"item": "minecraft:blaze_rod"
		}
	],
	"results": [],
	"processingTime": 1200,
	"superheated": true
}
```

配方规则:

* `ingredients` 必须且只能有一项, 且该项必须且只能定义 `item` 或 `tag` 中的一个.
* `item` 用于匹配单个物品.
* `tag` 用于匹配指定物品标签中的物品.
* `processingTime` 为必填项, 且必须大于 `0`.
* `results` 必填但必须为空数组.
* `superheated` 为可选布尔字段, 缺省为 `false`.
* `superheated` 为 `true` 时, 该燃料视为过热燃料, 燃烧时按 2.2 与 2.5 的规则处理.
* `superheated` 为 `false` 或缺失时, 不写入该字段.
* 自定义配方的 `processingTime` 覆盖原版燃料系统提供的燃烧时间.

## 4. 流体燃烧室

流体燃烧室用于消耗流体燃料并为锅炉提供热量.

流体燃烧室不得直接根据流体类型或流体属性判断燃料是否可燃, 必须通过自定义配方系统进行判断.

### 4.1 自定义流体燃料配方

流体燃烧室支持通过 RecipeType `steam_letters:fluid_fuel` 添加自定义流体燃料.

本配方同样继承机械动力的处理配方, 使用 Create 处理配方的 JSON 结构.

流体写在 `ingredients` 数组中, 且必须且只能有一项, 形如 `{"fluid": "..."}` 或 `{"fluidTag": "..."}`.

流体燃料的消耗量固定为 `1000mB`, 即 `amount` 必须为 `1000`.

配方中的 `processingTime` 表示消耗 `1000mB` 匹配流体能够持续燃烧的时间, 单位为 tick.

`results` 为必需字段, 本配方不产出流体, 固定为空数组.

配方格式如下:

单个流体:

```json
{
	"type": "steam_letters:fluid_fuel",
	"ingredients": [
		{
			"fluid": "minecraft:lava",
			"amount": 1000
		}
	],
	"results": [],
	"processingTime": 600
}
```

流体标签:

```json
{
	"type": "steam_letters:fluid_fuel",
	"ingredients": [
		{
			"fluidTag": "minecraft:lava",
			"amount": 1000
		}
	],
	"results": [],
	"processingTime": 600
}
```

过热燃料:

```json
{
	"type": "steam_letters:fluid_fuel",
	"ingredients": [
		{
			"fluid": "minecraft:lava",
			"amount": 1000
		}
	],
	"results": [],
	"processingTime": 600,
	"superheated": true
}
```

配方规则:

* `ingredients` 必须且只能有一项, 且该项必须且只能定义 `fluid` 或 `fluidTag` 中的一个.
* `fluid` 用于匹配单个流体.
* `fluidTag` 用于匹配指定流体标签中的流体.
* `amount` 必须为 `1000`.
* `processingTime` 为必填项, 且必须大于 `0`.
* `results` 必填但必须为空数组.
* `superheated` 为可选布尔字段, 缺省为 `false`.
* `superheated` 为 `true` 时, 该流体燃料视为过热燃料, 燃烧时按 2.2 与 2.5 的规则处理.
* `superheated` 为 `false` 或缺失时, 不写入该字段.
* 每次开始新一轮燃烧时, 消耗 `1000mB` 匹配流体.
* 如果剩余流体不足 `1000mB`, 不得开始新一轮燃烧.
* 当前燃烧过程的剩余时间独立于 Tank 中的流体存量.
* 当前燃烧过程结束后, 如果存在足够的下一份燃料, 则可以开始下一轮燃烧.
* 配方不得存在其他可选字段.

### 4.2 流体存储

* 流体燃烧室的内部 Tank 容量由注册参数 `capacity(number)` 决定.
* 流体燃烧室的 `capacity` 默认为 `1000`, `maxHeat` 默认为 `100.0`.
* 内部 Tank 支持正常的流体能力交互.
* 只有匹配有效燃料配方的流体才能被消耗.
* 输入流体不得在未匹配配方或未启动燃烧的情况下被无故销毁.

## 5. 蒸汽飞轮与飞轮引擎

本次新增蒸汽飞轮和飞轮引擎, 用于扩展 Create 的动力系统.

两者永远成对注册, 统一使用注册类型 `steam_letters:engine_and_flywheel`.

具体工作机制, 应力提供规则, 蒸汽消耗规则以及飞轮的储能行为, 需要结合项目现有的 Create 动力系统进行设计.

实现前必须先检查项目现有的动力接口, 并列出尚未确定的核心参数, 不得自行引入与现有动力系统冲突的机制.

引擎运转时的表现与连杆行程绑定: 连杆每走到行程的一端释放一次蒸汽, 也就是飞轮每一转释放两次. 释放时在引擎端口同时播放音效与粒子,
音效沿用 SteamPowered 蒸汽引擎的熄火声 (`minecraft:block.fire.extinguish`, 音量与音高均为 0.25), 释放频率因此跟随转速变化,
不采用固定间隔.

## 6. KubeJS 注册接口

本模组的设备通过 KubeJS 的 Startup 注册事件注册, 每个设备对应一个独立的注册类型:

* `steam_letters:boiler` 锅炉
* `steam_letters:solar` 太阳能锅炉
* `steam_letters:solid_burner` 固体燃烧室
* `steam_letters:fluid_burner` 流体燃烧室

方块的 ID 完全跟随脚本给出的 ID, 不写命名空间时默认为 `kubejs`, 因此
`event.create("steel_boiler", "steam_letters:boiler")` 注册出的方块是 `kubejs:steel_boiler`.

每次 `event.create` 调用只注册一个方块, 不得因为使用相同的设备实现类型而重复注册同一个方块 ID.

### 6.1 通用注册参数

* `capacity(number)` 流体存储容量, 单位为 mB.
* `production(number)` 满效率基础蒸汽产出速率, 单位为 mB/tick.
* `maxHeat(number)` 燃烧室能够达到的最大热量.
* `material(ResourceLocation)` 模型与贴图使用的命名空间和路径.
* `model(ResourceLocation)` 直接指定模型路径.

不写的参数使用对应设备类中声明的默认值, 与设备无关的参数不需要填写.

以上参数可以按任意顺序书写: 每个 builder 的配置方法都返回具体设备自己的 builder 类型, `material` / `model`
写在最前面也不会把类型退化成通用基类, 写完之后仍然能继续调用 `capacity` / `production` / `maxHeat` 等设备专属参数.

注册参数不写入配置文件, 各设备的注册参数默认值在对应设备类中声明.

`material` 和 `model` 都接收 ResourceLocation, 命名空间用于区分模型与贴图从哪个模组取:

* 不写 `model` 时, 模型路径为 `<设备目录>/<material 的 path>`, 例如锅炉上写 `material("steam_letters:steel")` 得到模型
  `steam_letters:block/steam/boiler/steel`.
* 写了 `model("命名空间:模型路径")` 时以它为准, `material` 只作为兜底.
* 贴图目录与模型路径相同, 按部件取 `side` `top` `down` `off` `on`.

### 6.2 锅炉

```js
StartupEvents.registry("block", (event) => {
	event.create("steel_boiler", "steam_letters:boiler")
		.material("steam_letters:steel")
		.capacity(8000)
		.production(24.0)
})
```

### 6.3 太阳能锅炉

```js
StartupEvents.registry("block", (event) => {
	event.create("steel_solar_boiler", "steam_letters:solar")
		.material("steam_letters:steel")
		.capacity(8000)
		.production(16.0)
})
```

太阳能锅炉沿用它本身那套 Blockbench 造型 (四面围墙加一块玻璃盖), 生成器内联内置的 bronze 造型作骨架, 只把 `side` `top`
`down` 三张贴图换成该材质的, 所以在 KubeJS 资源目录里按 6.5 放这三张图即可. 材质为 `steam_letters:bronze` 时直接复用内置资源,
不重复生成模型.

### 6.4 固体燃烧室与流体燃烧室

```js
StartupEvents.registry("block", (event) => {
	// 固体燃烧室
	event.create("steel_solid_burner", "steam_letters:solid_burner")
		.material("steam_letters:steel")
		.maxHeat(100)

	// 流体燃烧室
	event.create("steel_fluid_burner", "steam_letters:fluid_burner")
		.material("steam_letters:steel")
		.capacity(1000)
		.maxHeat(100)
})
```

燃烧室带有水平朝向和点燃状态, 资源生成会产出 `facing` 与 `lit` 的全部组合, 以及点燃前后的两份模型 `<模型路径>` 与
`<模型路径>_lit`.

### 6.5 资源生成与语言

方块对应的 blockstate, 方块模型和物品模型都由注册器在客户端资源生成阶段产出, 不需要手写 json. 只有贴图需要放在 KubeJS
的资源目录:

```
kubejs/assets/<命名空间>/textures/block/steam/<设备>/<材质>/<部件>.png
```

注册器会按方块 ID 自动生成英文名, 例如 `steel_boiler` 显示为 `Steel Boiler`. 其他语言在资源包里补充
`block.<命名空间>.<方块 ID>`.

### 6.6 燃料配方

两种燃料配方都通过 KubeJS 注册, 位置参数统一为 `steam_letters.<类型>(fuel, time)`, 并支持链式方法
`.superheated(boolean?)`.

| 配方类型                   | KubeJS 写法                            | 适用设备   |
|----------------------------|----------------------------------------|------------|
| `steam_letters:solid_fuel` | `steam_letters.solid_fuel(fuel, time)` | 固体燃烧室 |
| `steam_letters:fluid_fuel` | `steam_letters.fluid_fuel(fuel, time)` | 流体燃烧室 |

`fuel` 给物品或流体的 ID 字符串, 带 `#` 前缀表示标签. `time` 是燃烧时长, 单位为 tick.

`.superheated(value)` 把这份燃料标记为过热燃料, 规则见 2.2 与 2.5. 省略参数等价于 `false`.

```js
ServerEvents.recipes((event) => {
	let {steam_letters} = event.getRecipes()

	steam_letters.solid_fuel("minecraft:diamond", 20 * 60)
	steam_letters.solid_fuel("#minecraft:coals", 20 * 30)
	steam_letters.fluid_fuel("minecraft:lava", 20 * 30)
	steam_letters.fluid_fuel("#minecraft:lava", 20 * 30)

	// 过热燃料: 升温更快, 可以让锅炉产过热蒸汽
	steam_letters.solid_fuel("minecraft:blaze_rod", 20 * 60).superheated(true)
	steam_letters.fluid_fuel("minecraft:lava", 20 * 30).superheated()
})
```

流体配方不需要写消耗量, 每次固定消耗 1000 mB.

### 6.7 蒸汽飞轮与飞轮引擎

蒸汽飞轮和飞轮引擎使用同一个设备实现类型 `steam_letters:engine_and_flywheel`. 一条 `event.create` 产出两个方块:
脚本 id 只当材质前缀, 引擎 id 在它后面追加 `_steam_engine`, 飞轮再把 `_steam_engine` 换成 `_steam_flywheel`.

```js
StartupEvents.registry("block", (event) => {
	// cmi:cast_iron -> cmi:cast_iron_steam_engine (引擎) + cmi:cast_iron_steam_flywheel (飞轮)
	event.create("cmi:cast_iron", "steam_letters:engine_and_flywheel")
		// 材质资源, 与 6.1 的 material 相同: 决定模型与贴图来源
		.material("steam_letters:cast_iron")
		// 应力参数, 具体含义需要与设备类型对应
		.strength(number)
		// 输出转速, 单位为 RPM
		.speed(number)
		// 满负荷基础消耗速率, 单位为 mB/tick
		.consumption(number)
		// 自带蒸汽罐容量, 单位为 mB
		.capacity(number)
})
```

引擎不能脱离飞轮单独注册, 所以没有"只注册引擎"的写法: 脚本 id 已经带 `_steam_engine` 时不再重复追加后缀.
两个方块各自拥有独立的方块实体类型与方块物品, 以及各自的 blockstate, 方块模型, 物品模型与语言条目.
两个物品的标签也跟着走: 引擎物品进 `steam_letters:steam_engine`, 飞轮物品进 `steam_letters:steam_flywheel`.

模型与贴图在注册阶段自动生成, 脚本只需要给材质名:

* 没写 `model` 且材质不是内置的 `bronze` 时, 注册器把同名 bronze 模型的造型直接内联进生成结果, 只替换贴图,
  自动生成引擎与飞轮的方块模型与物品模型.
* 生成物和锅炉, 燃烧室一样是完整的自包含模型, 由 KubeJS 写进虚拟资源包 (`assets/<命名空间>/models/...`), 不 parent
  到模组内置资源, 因此不依赖内置模型文件是否存在.
* 贴图按 材质命名空间 + 部件后缀 自动识别: `<材质命名空间>:block/steam/flywheel/<材质>_wheel`,
  `<材质命名空间>:block/steam/casing/<材质>_casing`, `<材质命名空间>:block/steam/gearbox/<材质>_gearbox`,
  `<材质命名空间>:block/steam/engine/<材质>_cylinder`, `<材质命名空间>:block/steam/metal_block/<材质>_block`.
* 材质为 `steam_letters:bronze` 时直接复用内置模型, 不生成任何覆盖文件.
* 只有想让材质拥有独立造型时才显式写 `model("命名空间:模型路径")`, 此时自动生成会被跳过.

飞轮的 **渲染**同样按材质走: 轮盘与四根传动杆都取与材质同名的模型.

* 轮盘模型取 `<材质命名空间>:block/steam/flywheel/<材质>_wheel`.
* 四根传动杆分别取 `<材质命名空间>:block/steam/flywheel/<材质>_upper_rotating_connector`, `_lower_rotating_connector`,
  `_upper_sliding_connector`, `_lower_sliding_connector`.
* 这些模型由注册器在注册阶段连同外壳一起生成: 内联 bronze 同名模型的造型, 只把贴图键 `0` 与 `particle` 换成
  `<材质命名空间>:block/steam/flywheel/<材质>_wheel`, 写进 KubeJS 虚拟资源包, 因此不需要单独准备连杆的贴图.
* 渲染侧由 `SlBlockPartialModel.flywheelWheel(材质)` 与 `flywheelConnector(材质, 部件)` 取模型; 材质为
  `steam_letters:bronze` 时直接返回模组内置的 `bronze_wheel` 与四根 bronze 传动杆常量, 其余材质按材质缓存 partial.
* Flywheel 的 `PartialModel` 只有在模型烘焙 (`ModelEvent.RegisterAdditional`) 之前已经创建, 才会被加进模型加载列表;
  等到渲染时才创建, 拿到的永远是 missing model, 方块会显示成紫黑方块. 因此客户端在 `FMLClientSetupEvent` 里遍历注册表,
  对每个 `SteamFlywheelBlock` 的材质调用 `SlBlockPartialModel.preloadFlywheel(材质)` 预建轮盘与四根传动杆的 partial,
  不得在渲染阶段惰性创建.
* KubeJS 动态注册出来的飞轮带着自己的方块实体类型, 走不到 Registrate 的 `visual` / `renderer` 链: 客户端在
  `FMLClientSetupEvent` 里用 `SimpleBlockEntityVisualizer` 给这些类型补挂 `SteamFlywheelInstance`, 在
  `EntityRenderersEvent.RegisterRenderers` 里补挂 `SteamFlywheelRenderer`, 两者都按方向与转速复用与内置飞轮相同的动效.

具体规则:

* `strength(number)` 应力参数, 单位为 `SU`, 飞轮引擎默认为 `16384.0`.
* `strength` 是动力网络里的 **总应力容量**, 不是每 RPM 容量: Create 的 `KineticNetwork` 按 `capacity × |转速|` 累计总容量,
  因此发电机必须把总容量除以自身转速后再交给网络, 不得直接把 `strength` 当作 `calculateAddedStressCapacity()` 的返回值.
* `speed(number)` 输出转速, 单位为 `RPM`, 飞轮引擎默认为 `32.0`.
* `consumption(number)` 满负荷基础蒸汽消耗速率, 单位为 `mB/tick`, 飞轮引擎默认为 `12.0`.
* 同材料锅炉的最高产汽速率 (`production` × `100%` 效率) 与该 `consumption` 相等: 一台满负荷引擎恰好消耗掉一台同材料锅炉的全部产出.
* `capacity(number)` 设备自带蒸汽罐容量, 单位为 `mB`, 飞轮引擎默认为 `32000`.
* 从锅炉直抽蒸汽的效率不通过注册参数设置, 由配置文件的 `steam_engine.suck_efficiency` 对所有飞轮引擎统一控制, 默认为
  `0.75`.
* 引擎每 tick 从汽源抽取的蒸汽量不超过满负荷消耗速率 `consumption`.
* 直抽效率作用在入账侧: 引擎从汽源抽走的蒸汽只有 `suck_efficiency` 的部分计入引擎, 应力输出按计入量计算.
* 蒸汽结算以一个 tick 为周期: 该 tick 没有抽到需求的量, 不累积到下一个 tick.
* 预热时长由配置文件的 `steam_engine.heatup_seconds` 单独决定, 默认为 `2.0` 秒 (`40` tick), 不再按 `consumption` 推算;
  使用过热蒸汽时按 `superheated_acceleration_multiplier` 缩短预热时长, 默认 `2.0` 即减半.
* 预热期间的蒸汽需求按预热时长四等分阶梯递增: 每段消耗满负荷的 `25%`, `50%`, `75%`, `100%`, 默认 2 秒即每 `10` tick 升一档,
  `30` tick 之后为满消耗.
* 短暂断汽不清空预热进度: 连续 `20` tick 抽不到蒸汽才判定停机, 避免汽源产汽与引擎抽取的节律错拍导致引擎在预热与停机之间跳动.
* 预热与待机时飞轮硬停机 (直接清空转速与应力容量), 不走停机的 `40` tick 平滑缓冲; 平滑缓冲会让飞轮保留上一次的转速与容量继续挂在动力网络上,
  表现为引擎已停汽却仍在旋转并输出应力.
* 各参数的适用设备, 实际含义和单位必须在注册器实现中明确.
* 不得为不需要相关参数的设备强行设置无意义的默认值.
* 所有动力计算必须遵循 Create 现有的应力系统规则.
* 如果飞轮和飞轮引擎的参数含义不同, 必须通过明确的设备类型区分, 不得让同一参数在不同设备中产生无法解释的行为.

### 6.8 蒸汽锻锤具体功能

蒸汽锻锤是一个继承Create原版`动力辊压机`(mechanical_press)的设备, 与机械动力原版的辊压机最大的区别是

* 运行蒸汽锻锤需要向其中注入蒸汽, 运行过程中会消耗蒸汽锻锤的蒸汽储量
* 蒸汽锻锤可以并行处理最高64个配方, 包括冲压配方, 压块塑形配方以及其他Create附属mod添加的动力辊压机配方

### 6.9 蒸汽搅拌机具体功能

蒸汽搅拌机是一个继承Create原版`动力搅拌机`(mechanical_mixer)的设备, 与机械动力原版的搅拌机最大的区别是

* 运行蒸汽搅拌机需要向其中注入蒸汽, 运行过程中会消耗蒸汽搅拌机中的蒸汽储量
* 蒸汽搅拌机可以并行处理最高16个搅拌配方以及其他Create附属mod添加的动力搅拌机配方

### 6.10 高级注液器具体功能

高级注液器是一个继承Create原版`注液器`(spout)的设备, 与机械动力原版的注液器最大的区别是

* 运行速度更快, 5tick即可完成一个注液配方
* 拥有并行, 且允许从注液器侧面调整并行数量, 最低为1, 最高为20

### 6.11 青铜工作盆具体功能

青铜工作盆是一个继承Create原版`工作盆`(basin)的设备, 与机械动力原版的工作盆最大的区别是

* 每一个FluidSlot拥有原版工作盆16倍的储量

### 6.12 青铜蒸汽泵具体功能

青铜蒸汽泵是一个继承Create原版`动力泵`(mechanical_pump)的设备, 与机械动力原版的动力泵最大的区别是

* 青铜蒸汽泵不需要输入应力, 可以直接向Create管道中泵送蒸汽
* 青铜蒸汽泵只能泵送蒸汽和过热蒸汽, 其他的任何流体都无法泵送

### 6.13 蒸汽锯具体功能

蒸汽锯是一个继承Create原版`动力锯`(mechanical_saw)的设备, 与机械动力原版的动力锯最大的区别是

* 运行蒸汽锯需要向其中注入蒸汽, 运行过程中会消耗蒸汽锯中的蒸汽储量
* 蒸汽锯可以并行处理64个切割配方以及其他Create附属mod添加的动力锯配方

## 7. 通用实现要求

### 7.1 数据持久化

* 燃烧室必须保存当前热量, 剩余燃烧时间以及必要的燃料状态.
* 太阳能锅炉和锅炉必须正确保存内部流体.
* 所有设备在区块卸载, 重新加载和游戏重启后, 必须正确恢复持久化数据.
* 不得因设备重新加载而无故重置热量, 燃烧时间或流体存量.

### 7.2 服务端与客户端

* 实际燃料消耗, 流体消耗, 蒸汽生产和动力计算必须在服务端执行.
* 客户端只负责显示和同步必要的设备状态.
* 不得在客户端重复执行实际资源消耗逻辑.

### 7.3 性能

* 不得在每个 tick 执行不必要的配方扫描.
* 不得在每个 tick 执行不必要的全范围方块检查.
* 太阳能锅炉的环境判定应尽可能复用已有结果, 避免重复执行高开销检测.
* 设备状态只有在必要时才进行同步和更新.

### 7.4 代码范围

* 优先复用项目已有的注册器, 配置系统, 配方系统, 流体处理接口和动力接口.
* 不得为了实现本次功能而重写无关系统.
* 不得擅自修改已有设备的工作机制.
* 如果需要修改公共接口, 必须说明修改原因和影响范围.
* 完成后检查编译错误, 配方加载, 流体交互, 存档读写, 服务端逻辑和 KubeJS 注册流程.

## 8. 实现流程

1. 检查项目现有架构, 确认本次功能可以复用的代码.
2. 列出尚未确定的核心参数和存在歧义的规则.
3. 在开始实现前, 明确需要用户确认的问题.
4. 确认设计后, 再开始修改代码.
5. 完成后列出新增和修改的文件, 并说明各文件的作用.
6. 检查编译结果以及主要功能的运行逻辑.
