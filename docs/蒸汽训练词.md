接下来我需要你实现几个比较大的功能, 主要涉及蒸汽的获取、燃料的消耗以及动力的产生.

# 声明与约定

* `(C)` 表示可配置, 所有可配置参数必须提供明确的默认值.
* 蒸汽和水的转换比例为 `1:1`, 即消耗 `1mB` 水产生 `1mB` 蒸汽.
* 时间单位优先使用 Minecraft tick, 默认 `20 tick = 1秒`.
* 流体容量的单位为 `mB`.
* 生产速率和消耗速率的单位为 `mB/tick`.
* 为了整合包的兼容性, 锅炉输出的蒸汽默认为 `steam_letters:steam`, 但允许通过配置文件修改输出蒸汽的流体 ID.
* 修改蒸汽流体配置时, 不得自动转换、清除或销毁世界内已有的流体. 如果需要清理旧流体, 由整合包开发者自行处理, 以避免不必要的性能开销.
* 所有设备必须正确处理客户端与服务端的逻辑, 实际的燃料消耗、流体消耗和生产计算必须在服务端执行.
* 所有需要持久化的数据必须正确保存和读取, 避免设备因区块卸载、重新加载或游戏重启而丢失工作状态.
* 实现前必须先检查项目现有的方块注册、BlockEntity、配置、配方、流体和动力系统, 优先复用现有架构.
* 如果需求存在歧义或缺少必要参数, 应先列出需要确认的问题, 不得擅自决定核心机制.

# 用法与工作机制

## 1. 太阳能锅炉

太阳能锅炉是一种能够利用太阳光或人造光, 消耗内部存储的水并将其转换为蒸汽的设备.

### 1.1 太阳光条件

* 检查设备正上方 1 至 16 格的空间.
* 如果检查范围内不存在符合遮罩判定条件的方块, 则满足无遮挡条件.
* 玻璃、树叶以及其他非完整方块按照透明方块处理, 不构成太阳光遮罩.
* 太阳光条件下的基础效率为 `100% (C)`.

### 1.2 人造光条件

* 当太阳光条件不满足时, 可以尝试通过人造光满足工作条件.
* 人造光的最低光照等级默认为 `8 (C)`.
* 满足人造光条件时, 基础效率为 `50% (C)`.

### 1.3 天气影响

* 普通雨天的效率系数为 `50% (C)`.
* 雷雨天的效率系数为 `25% (C)`, 包括雷雨期间的降雪天气.
* 天气效率系数乘以当前光照条件的基础效率.
* 天气影响不得与基础光照效率混淆.

例如, 人造光基础效率为 `50%`, 普通雨天效率系数为 `50%`, 则最终效率为 `25%`.

### 1.4 末地规则

* 末地环境下, 如果设备满足无遮挡条件, 则光照效率为 `100%`.
* 如果设备受到遮罩, 则尝试按照人造光规则判断是否能够工作.
* 末地规则覆盖普通光照效率和天气效率规则, 不受天气影响.

### 1.5 蒸汽生产

* 太阳能锅炉的基础产出速率由注册参数 `production(number)` 决定.
* `production` 表示设备在 `100%` 效率下每 tick 的基础蒸汽产出量, 单位为 `mB/tick`.
* 太阳能锅炉的 `capacity` 默认为 `4000`, `production` 默认为 `20.0`.
* 实际生产速率等于基础产出速率乘以当前环境效率.
* 太阳能锅炉的内部水量不足或蒸汽存储空间不足时, 不得消耗超过实际生产需求的水.
* 蒸汽生产必须支持小数累计, 不得因为每次计算取整而丢失流体.
* 设备停止工作时, 保留内部已有的水和蒸汽.

## 2. 燃烧室与锅炉

燃烧室和锅炉是一套设施, 由两个独立方块组成.

* 燃烧室位于下方.
* 锅炉位于燃烧室上方.
* 燃烧室负责消耗燃料并产生热量.
* 锅炉负责消耗水并生产蒸汽.
* 固体燃烧室和流体燃烧室使用相同的热量机制, 但燃料获取方式不同.

### 2.1 基本工作流程

1. 在燃烧室中输入燃料.
2. 燃烧室开始消耗燃料并升温.
3. 锅炉检测正下方是否存在有效的燃烧室.
4. 当燃烧室热量达到规定条件且锅炉内部存在水时, 锅炉开始生产蒸汽.
5. 当燃料耗尽且没有新的燃料输入时, 燃烧室停止升温并开始降温.
6. 当燃烧室热量低于工作要求时, 锅炉停止生产蒸汽.

### 2.2 热量机制

燃烧室的热量范围为 `0-100`, 初始热量为 `0`.

* 输入有效燃料后, 燃烧室开始工作.
* 燃烧室每 `2 tick` 增加 `1` 点热量, 直到达到 `100`.
* 燃烧室达到 `100` 点热量后, 不再继续升温.
* 燃料的燃烧时间由对应燃料系统决定.
* 固体燃料和流体燃料本身只决定燃烧持续时间, 不直接决定升温速度.
* 燃烧室有燃料燃烧时, 即使热量已达到 `100`, 燃料仍然持续消耗.
* 当当前燃料耗尽且没有新的燃料输入时, 燃烧室停止升温并开始降温.
* 降温速度应当使用统一的配置参数, 具体默认值需要在实现前确认.
* 热量不得超过 `100`, 也不得低于 `0`.

燃烧室负责维护自身的热量数据.

锅炉直接读取正下方燃烧室的当前热量, 不需要额外维护一份重复的热量数据.

如果锅炉正下方不存在有效燃烧室, 或燃烧室被移除、替换, 则锅炉必须停止生产蒸汽.

### 2.3 锅炉运行效率

锅炉的运行效率根据燃烧室当前热量采用阶梯式计算, 而不是线性计算.

| 燃烧室热量 | 锅炉运行效率 |
| ---------- | ------------ |
| `0-24`     | `0%`         |
| `25-49`    | `25%`        |
| `50-74`    | `50%`        |
| `75-99`    | `75%`        |
| `100`      | `100%`       |

具体规则如下:

* 热量低于 `25` 时, 锅炉停止生产蒸汽.
* 热量达到 `25` 时, 锅炉以基础产出速率的 `25%` 运行.
* 热量达到 `50` 时, 锅炉以基础产出速率的 `50%` 运行.
* 热量达到 `75` 时, 锅炉以基础产出速率的 `75%` 运行.
* 热量达到 `100` 时, 锅炉以 `100%` 的基础产出速率运行.
* 燃烧室降温时, 锅炉根据当前热量重新计算运行效率.

### 2.4 锅炉流体存储

锅炉的 BlockEntity 拥有两个 FluidTank, 两个 Tank 的容量相同.

* 输入 Tank 仅接受水流体.
* 输出 Tank 仅接受配置文件指定的蒸汽流体.
* 两个 Tank 均支持正常的流体能力交互.
* 输入和输出 Tank 的容量均由注册参数 `capacity(number)` 决定.
* 输出 Tank 容量不足时, 锅炉不得消耗超过实际可生产容量的水.
* 锅炉停止工作时, 保留两个 Tank 中的现有流体.
* 不得在流体生产过程中无故销毁水或蒸汽.
* 修改蒸汽流体配置后, 不得自动替换现有 Tank 中的流体.
* 蒸汽生产必须支持小数累计, 不得因为每次计算取整而丢失流体.

锅炉的基础产出速率由注册参数 `production(number)` 决定.

`production` 表示锅炉在 `100%` 运行效率下每 tick 的基础蒸汽产出量, 单位为 `mB/tick`.

实际生产速率等于基础产出速率乘以当前锅炉运行效率.

锅炉的 `capacity` 默认为 `10000`, `production` 默认为 `100.0`.

## 3. 固体燃烧室

固体燃烧室用于消耗物品燃料并为锅炉提供热量.

### 3.1 原版燃料支持

* 固体燃烧室默认支持所有被原版熔炉燃料系统识别为可燃燃料的物品.
* 原版燃料的基础燃烧时间使用原版燃料系统提供的燃烧时间.
* 如果物品既匹配自定义燃料配方, 又属于原版燃料, 则优先使用自定义配方的 `time`.
* 如果没有匹配到自定义燃料配方, 则回退到原版熔炉燃料系统.
* 如果两者均不匹配, 则物品不能作为燃料.

固体燃烧室的 `maxHeat` 默认为 `100.0`.

### 3.2 自定义固体燃料配方

固体燃烧室支持通过 RecipeType `steam_letters:solid_fuel` 添加自定义固体燃料.

配方支持以下数据类型:

* `net.minecraft.world.item.crafting.Ingredient`
* `int`

其中, `Ingredient` 用于定义燃料物品的匹配条件, `int` 用于定义燃烧时间.

燃烧时间的单位为 tick, 表示该燃料能够持续燃烧的时间.

配方格式如下:

单个物品:

```json
{
    "type": "steam_letters:solid_fuel",
    "item": "minecraft:diamond",
    "time": 1200
}
```

物品标签:

```json
{
    "type": "steam_letters:solid_fuel",
    "tag": "forge:ingots/iron",
    "time": 600
}
```

配方规则:

* 配方必须且只能定义 `item` 或 `tag` 中的一个.
* `item` 用于匹配单个物品.
* `tag` 用于匹配指定物品标签中的物品.
* `time` 为必填项, 且必须大于 `0`.
* 配方不得存在其他可选字段.
* 自定义配方的 `time` 覆盖原版燃料系统提供的燃烧时间.

## 4. 流体燃烧室

流体燃烧室用于消耗流体燃料并为锅炉提供热量.

流体燃烧室不得直接根据流体类型或流体属性判断燃料是否可燃, 必须通过自定义配方系统进行判断.

### 4.1 自定义流体燃料配方

流体燃烧室支持通过 RecipeType `steam_letters:fluid_fuel` 添加自定义流体燃料.

配方支持以下数据类型:

* `com.simibubi.create.foundation.fluid.FluidIngredient`
* `int`

其中, `FluidIngredient` 用于定义流体匹配条件, `int` 用于定义燃烧时间.

流体燃料的消耗量固定为 `1000mB`, 因此配方不支持 `amount` 字段.

配方中的 `time` 表示消耗 `1000mB` 匹配流体能够持续燃烧的时间, 单位为 tick.

配方格式如下:

单个流体:

```json
{
    "type": "steam_letters:fluid_fuel",
    "fluid": "minecraft:lava",
    "time": 600
}
```

流体标签:

```json
{
    "type": "steam_letters:fluid_fuel",
    "fluidTag": "minecraft:lava",
    "time": 600
}
```

配方规则:

* 配方必须且只能定义 `fluid` 或 `fluidTag` 中的一个.
* `fluid` 用于匹配单个流体.
* `fluidTag` 用于匹配指定流体标签中的流体.
* `time` 为必填项, 且必须大于 `0`.
* 每次开始新一轮燃烧时, 消耗 `1000mB` 匹配流体.
* 如果剩余流体不足 `1000mB`, 不得开始新一轮燃烧.
* 当前燃烧过程的剩余时间独立于 Tank 中的流体存量.
* 当前燃烧过程结束后, 如果存在足够的下一份燃料, 则可以开始下一轮燃烧.
* 配方不得存在其他可选字段.

### 4.2 流体存储

* 流体燃烧室的内部 Tank 容量由注册参数 `capacity(number)` 决定.
* 流体燃烧室的 `capacity` 默认为 `1000`, `maxHeat` 默认为 `100.0`.
* 内部 Tank 支持正常的流体能力交互.
* 只有匹配有效燃料配方的流体才能被消耗.
* 输入流体不得在未匹配配方或未启动燃烧的情况下被无故销毁.

## 5. 蒸汽飞轮与飞轮引擎

本次新增蒸汽飞轮和飞轮引擎, 用于扩展 Create 的动力系统.

两者通过统一的注册类型 `steam_engine:flywheel_and_engine` 注册.

具体工作机制、应力提供规则、蒸汽消耗规则以及飞轮的储能行为, 需要结合项目现有的 Create 动力系统进行设计.

实现前必须先检查项目现有的动力接口, 并列出尚未确定的核心参数, 不得自行引入与现有动力系统冲突的机制.

## 6. KubeJS 注册接口

本模组的设备通过 KubeJS 的 Startup 注册事件注册, 每个设备对应一个独立的注册类型:

* `steam_letters:boiler` 锅炉
* `steam_letters:solar` 太阳能锅炉
* `steam_letters:solid_burner` 固体燃烧室
* `steam_letters:fluid_burner` 流体燃烧室

方块的 ID 完全跟随脚本给出的 ID, 不写命名空间时默认为 `kubejs`, 因此 `event.create("steel_boiler", "steam_letters:boiler")` 注册出的方块是 `kubejs:steel_boiler`.

每次 `event.create` 调用只注册一个方块, 不得因为使用相同的设备实现类型而重复注册同一个方块 ID.

### 6.1 通用注册参数

* `capacity(number)` 流体存储容量, 单位为 mB.
* `production(number)` 满效率基础蒸汽产出速率, 单位为 mB/tick.
* `maxHeat(number)` 燃烧室能够达到的最大热量.
* `material(ResourceLocation)` 模型与贴图使用的命名空间和路径.
* `model(ResourceLocation)` 直接指定模型路径.

不写的参数使用对应设备类中声明的默认值, 与设备无关的参数不需要填写.

注册参数不写入配置文件, 各设备的注册参数默认值在对应设备类中声明.

`material` 和 `model` 都接收 ResourceLocation, 命名空间用于区分模型与贴图从哪个模组取:

* 不写 `model` 时, 模型路径为 `<设备目录>/<material 的 path>`, 例如锅炉上写 `material("steam_letters:steel")` 得到模型 `steam_letters:block/steam/boiler/steel`.
* 写了 `model("命名空间:模型路径")` 时以它为准, `material` 只作为兜底.
* 贴图目录与模型路径相同, 按部件取 `side` `top` `down` `off` `on`.

### 6.2 锅炉

```js
StartupEvents.registry("block", (event) => {
    event.create("steel_boiler", "steam_letters:boiler")
        .material("steam_letters:steel")
        .capacity(8000)
        .production(24.0)
})
```

### 6.3 太阳能锅炉

```js
StartupEvents.registry("block", (event) => {
    event.create("steel_solar_boiler", "steam_letters:solar")
        .material("steam_letters:steel")
        .capacity(8000)
        .production(16.0)
})
```

### 6.4 固体燃烧室与流体燃烧室

```js
StartupEvents.registry("block", (event) => {
    // 固体燃烧室
    event.create("steel_solid_burner", "steam_letters:solid_burner")
        .material("steam_letters:steel")
        .maxHeat(100)

    // 流体燃烧室
    event.create("steel_fluid_burner", "steam_letters:fluid_burner")
        .material("steam_letters:steel")
        .capacity(1000)
        .maxHeat(100)
})
```

燃烧室带有水平朝向和点燃状态, 资源生成会产出 `facing` 与 `lit` 的全部组合, 以及点燃前后的两份模型 `<模型路径>` 与 `<模型路径>_lit`.

### 6.5 资源生成与语言

方块对应的 blockstate, 方块模型和物品模型都由注册器在客户端资源生成阶段产出, 不需要手写 json. 只有贴图需要放在 KubeJS 的资源目录:

```
kubejs/assets/<命名空间>/textures/block/steam/<设备>/<材质>/<部件>.png
```

注册器会按方块 ID 自动生成英文名, 例如 `steel_boiler` 显示为 `Steel Boiler`. 其他语言在资源包里补充 `block.<命名空间>.<方块 ID>`.

### 6.6 燃料配方

两种燃料配方都通过 KubeJS 注册, 形式统一为 `steam_letters.<类型>(fuel, time)`, 只有两个位置参数.

| 配方类型                   | KubeJS 写法                            | 适用设备   |
| -------------------------- | -------------------------------------- | ---------- |
| `steam_letters:solid_fuel` | `steam_letters.solid_fuel(fuel, time)` | 固体燃烧室 |
| `steam_letters:fluid_fuel` | `steam_letters.fluid_fuel(fuel, time)` | 流体燃烧室 |

`fuel` 给物品或流体的 ID 字符串, 带 `#` 前缀表示标签. `time` 是燃烧时长, 单位为 tick.

```js
ServerEvents.recipes((event) => {
	let { steam_letters } = event.getRecipes()

    steam_letters.solid_fuel("minecraft:diamond", 20 * 60)
    steam_letters.solid_fuel("#minecraft:coals", 20 * 30)
    steam_letters.fluid_fuel("minecraft:lava", 20 * 30)
    steam_letters.fluid_fuel("#minecraft:lava", 20 * 30)
})
```

流体配方不需要写消耗量, 每次固定消耗 1000 mB.

### 6.7 蒸汽飞轮与飞轮引擎

蒸汽飞轮和飞轮引擎使用统一的设备实现类型 `steam_engine:flywheel_and_engine`.

```js
StartupEvents.registry("block", (event) => {
    event.create(id, "steam_engine:flywheel_and_engine")
        // 应力参数, 具体含义需要与设备类型对应
        .strength(number)
        // 输出转速, 单位为 RPM
        .speed(number)
        // 满负荷基础消耗速率, 单位为 mB/tick
        .consumption(number)
        // 自带蒸汽罐容量, 单位为 mB
        .storage(number)
})
```

具体规则:

* `strength(number)` 应力参数, 单位为 `SU`, 飞轮引擎默认为 `16384.0`.
* `speed(number)` 输出转速, 单位为 `RPM`, 飞轮引擎默认为 `32.0`.
* `consumption(number)` 满负荷基础蒸汽消耗速率, 单位为 `mB/tick`, 飞轮引擎默认为 `12.0`.
* `storage(number)` 设备自带蒸汽罐容量, 单位为 `mB`, 飞轮引擎默认为 `32000`.
* 从锅炉直抽蒸汽的效率不通过注册参数设置, 由配置文件的 `steam_engine.suck_efficiency` 对所有飞轮引擎统一控制, 默认为 `0.75`.
* 各参数的适用设备、实际含义和单位必须在注册器实现中明确.
* 不得为不需要相关参数的设备强行设置无意义的默认值.
* 所有动力计算必须遵循 Create 现有的应力系统规则.
* 如果飞轮和飞轮引擎的参数含义不同, 必须通过明确的设备类型区分, 不得让同一参数在不同设备中产生无法解释的行为.

## 7. 通用实现要求

### 7.1 数据持久化

* 燃烧室必须保存当前热量、剩余燃烧时间以及必要的燃料状态.
* 太阳能锅炉和锅炉必须正确保存内部流体.
* 所有设备在区块卸载、重新加载和游戏重启后, 必须正确恢复持久化数据.
* 不得因设备重新加载而无故重置热量、燃烧时间或流体存量.

### 7.2 服务端与客户端

* 实际燃料消耗、流体消耗、蒸汽生产和动力计算必须在服务端执行.
* 客户端只负责显示和同步必要的设备状态.
* 不得在客户端重复执行实际资源消耗逻辑.

### 7.3 性能

* 不得在每个 tick 执行不必要的配方扫描.
* 不得在每个 tick 执行不必要的全范围方块检查.
* 太阳能锅炉的环境判定应尽可能复用已有结果, 避免重复执行高开销检测.
* 设备状态只有在必要时才进行同步和更新.

### 7.4 代码范围

* 优先复用项目已有的注册器、配置系统、配方系统、流体处理接口和动力接口.
* 不得为了实现本次功能而重写无关系统.
* 不得擅自修改已有设备的工作机制.
* 如果需要修改公共接口, 必须说明修改原因和影响范围.
* 完成后检查编译错误、配方加载、流体交互、存档读写、服务端逻辑和 KubeJS 注册流程.

## 8. 实现流程

1. 检查项目现有架构, 确认本次功能可以复用的代码.
2. 列出尚未确定的核心参数和存在歧义的规则.
3. 在开始实现前, 明确需要用户确认的问题.
4. 确认设计后, 再开始修改代码.
5. 完成后列出新增和修改的文件, 并说明各文件的作用.
6. 检查编译结果以及主要功能的运行逻辑.
